# 智能体框架

AIUI 智能体框架定义了如何把智能体描述、项目配置、页面和后台任务组织成一个可运行的项目。了解它们之间的关系，可以帮助你判断：**一个功能应该写在哪里，用户打开界面时又会发生什么。**

本页先介绍框架的主要组成和协作方式；各部分的完整写法可以在后续章节中查阅。

## 框架如何组织一个智能体？

一个 AIUI 项目通常由以下部分组成：

| 部分 | 负责什么 | 常见位置 |
| --- | --- | --- |
| 智能体描述 | 描述智能体的身份、能力和行为指令 | `AGENTS.md` |
| 应用配置 | 声明页面、可选入口和全局窗口配置 | `app.json` |
| 应用逻辑 | 处理应用级生命周期和共享数据 | `app.js` |
| Page | 承载页面数据、界面和用户操作 | `pages/` |
| Widget | 提供独立的小尺寸界面 | 通常放在 `widgets/` |
| Agent Worker | 执行不显示界面的后台任务 | 通常放在 `workers/` |

这几部分的职责不同：`AGENTS.md` 用来说明智能体是什么，`app.json` 声明项目有哪些入口，页面和其他代码则实现具体行为。**描述了某项能力，并不等于已经实现了该能力**；需要的数据、服务和处理逻辑仍需由开发者提供。

Page、Widget 和 Agent Worker 不需要全部使用。一个入门项目可以先只有一个页面，之后再按需求添加其他入口。

## 智能体和页面如何被打开？

AIUI 支持不同的交互方式，入口的设计也有所不同：

- **对话式页面**：页面可以通过 `description` 描述自己能完成什么，并通过 `schema.data` 描述打开时需要的数据。这样，对话中可以在合适的场景调用该页面，展示卡片等界面。
- **沉浸式智能体**：用户进入智能体后，通常从 `app.json` 中声明的第一个页面开始，再围绕独立界面继续操作。

例如，一个对话式页面可以声明自己接收 `city`。页面打开时，在 `onLoad(query)` 中读取这个输入；页面自己的 `data` 则用于保存和展示当前状态。两者的作用不同：**输入描述页面需要什么，页面数据记录界面当前显示什么**。

了解交互场景后，可以继续阅读[分类](./category.md)和[页面定义](/AIUI/framework/open-agent-format-page-definition)。

## 页面逻辑和界面如何配合？

页面可以用 `.ink` 文件组织配置、逻辑、界面结构和样式。常见的交互过程是：

1. 在页面的 `data` 中准备初始状态，通过 `{{ }}` 将数据绑定到界面。
2. 用 `bindtap` 等事件绑定把用户操作关联到处理函数。
3. 在处理函数中调用 `this.setData()` 更新数据，受影响的界面内容随之更新。

页面也可以使用生命周期函数，例如在 `onLoad()` 中读取输入，在 `onUnload()` 中清理资源。页面隐藏、重新显示或卸载时，处理逻辑应与相应生命周期配合。

Page 和 Widget 都可以使用数据绑定、组件、事件和样式，但它们是不同的入口，生命周期也不同。完整示例见[逻辑开发](./logic.md)和[用户界面（UI）开发](./ui.md)；一次界面更新的过程见[运行机制](../runtime/mechanism.md)。

## 什么时候使用 Widget 或 Agent Worker？

**Widget** 适合需要快速查看或操作的小尺寸界面，例如设备状态。它有独立入口，在 `app.json` 中声明，使用自己的生命周期；配置和完整示例见 [Widget 开发](/AIUI/framework/open-agent-format-widget)。

**Agent Worker** 适合不需要显示界面的任务，例如一次性初始化，或在多个 Page、Widget 打开期间维护共享任务。它需要在 `app.json` 中声明，具有独立的运行环境；不能把页面里的界面对象或所有页面 API 当作 Worker 可用。运行时长和能力限制见 [Agent Worker 开发](/AIUI/framework/open-agent-format-agent-worker)。

如果功能只属于当前页面，先把逻辑放在页面中即可。需要小尺寸独立界面或共享后台任务时，再考虑增加 Widget 或 Worker。

## 框架与运行时分别负责什么？

框架提供组织项目和编写智能体的约定，例如页面配置、数据绑定、事件和生命周期。运行时负责加载项目、执行代码、处理事件并展示界面。应用可以通过 API 使用网络、存储等能力；具体可用性和使用条件以相应 API 文档为准。

开发时可以先用模拟环境检查，再在目标设备上验证显示、输入和性能。涉及不同显示能力时，参考[全彩眼镜适配](./full-color.md)。
